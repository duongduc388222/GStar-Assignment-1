# GStar Assignment 1 — FlashAttention and its variants

**Duc Duong**

Before this assignment I had already implemented attention sinks and sliding-window attention (SWA), but I had never implemented grouped-query attention (GQA) or FlashAttention, and I had never written a GPU kernel. So I learned these in a backwards order. This turned out to help, because building the kernels showed me how SWA and sinks affect the KV cache and the cost of LLM inference on the hardware, not just the attention mask.

The assignment builds one attention kernel step by step. It starts as tiled FlashAttention in PyTorch, moves to Triton, and then adds causal masking, GQA, SWA and sinks on top of the same core. That core is the online softmax. Queries are processed in blocks, and each block keeps a running max, a running softmax denominator and an unnormalised output. For every block of keys and values, the kernel computes the scores, masks the ones that are not allowed, updates the max, rescales what it has accumulated so far, and adds the new block's contribution. The result is exactly the same as normal attention. The gain comes from never storing the full N×N score matrix, so memory grows linearly with sequence length, and each K/V block is read from GPU memory once per query block.

Once that loop worked, every variant was mostly a change to which K/V blocks the loop visits and how they are indexed. Causal attention skips key blocks that come after the query block and only masks the blocks on the diagonal, so about half of the K/V reads disappear. GQA changes one line of pointer arithmetic so that several query heads read the same K/V head, which shrinks the KV cache and its memory traffic by the group size. SWA moves the start of the loop so each query only loads keys inside its window, which makes the cost depend on the window size instead of the sequence length. Sinks add a small extra pass over the first few tokens before the window. Seeing all four this way made it clear why they matter for inference. They decide how large the KV cache is, which parts of it must stay in memory, and how much of it is read for every new token. A fixed-size window plus a few sink tokens is what makes streaming inference possible.

Most of my bugs came from details rather than the main idea. My first causal mask used positions inside the tile instead of absolute token positions, which masked the wrong entries in off-diagonal tiles. With sliding windows, some rows can be fully masked before they have seen any valid key, which produces NaN from −inf − (−inf) unless it is handled. Precision also mattered more than I expected. My first Triton kernel did its multiplications in fp32 and failed the autograder, because the reference multiplies in bf16 and those rounding differences add up over thousands of values. Matching the reference's precision, with bf16 inputs and fp32 accumulation, was part of getting the right answer.

Overall, I learned that FlashAttention and its variants are about controlling memory movement on the GPU. I already knew SWA and sinks as masking rules, but implementing them inside a kernel showed me how they connect to the KV cache and to the real cost of running an LLM.
